## 开场：一个真实的问题

【先不翻到幻灯片，直接面向听众】

我给大家讲一件真事。1984 年 12 月 3 日凌晨，印度博帕尔市一家农药厂发生异氰酸甲酯泄漏，造成数千人死亡，是工业史上最严重的化工灾难。事后调查发现，事故不是一夜之间发生的——在这之前的几个月里，工厂的冷却系统就已经出过问题、安全阀也被拆掉了、操作员也提出过警告。但是这些信息散落在不同部门的交接班记录里，没有人能把这些碎片拼起来，看到 "冷却系统故障 → 温度升高 → 储罐超压 → 泄漏" 这条完整的因果链。

40 年过去了。今天中国的化工厂有 DCS 控制系统、有 CAS 安全仪表系统，技术好多了。但是事故调查报告的知识管理方式，本质上没有变。

【翻到化工事故数据页】

2023 年，全国化工事故 120 多起。每一起事故之后，应急管理部门都会发布调查报告——哪台设备先出了问题、什么操作违规了、事故怎么一步步扩大的、最后给了什么整改建议。这些报告是非常珍贵的知识资产。但是它们现在的状态是什么？PDF 文件，散落在各个政府网站和行业平台上。

一个化工厂的安全管理人员，要为一个新项目做 HAZOP 分析——危险与可操作性分析。他想查一下历史上类似工艺、类似化学品发生过什么事故。他怎么查？他只能凭记忆和经验去翻以前的报告。如果记忆里没有，他就查不到。

这就是我们想解决的问题。

## 三个致命缺陷：为什么纯 LLM 不够

你可能会说——"现在大模型这么强，把报告喂给 ChatGPT，让它直接问答不就行了？"

我们在立项之前做了大量的调研和实验，发现纯 LLM 在化工安全领域有三个绕不过去的坑。

第一个——**领域幻觉**。化工有极其专业的术语体系和工艺逻辑。"光气化反应釜尾气破坏器联锁摘除"——这 15 个字，每一个字 LLM 都认识，但把它们放在一起是什么意思，LLM 不理解。它会基于字面去猜。猜的结果听起来可能很像那么回事，但实际上错得离谱。在化工安全这个领域，"听起来合理"和"事实上正确"之间的距离可以致命。

第二个——**知识时效性问题**。大模型的知识截止于训练数据切点。比如最新一起事故的调查报告是上个月才发布的，模型不可能知道。而化工安全恰恰需要最新的案例来汲取教训。

第三个——**多跳逻辑断裂**。这是三个问题里最关键的。一起化工事故从来不会一步到位——理想情况下，事故链条有六七步：某台泵坏了 → 冷却中断 → 储罐温度慢慢上去了 → 高温触发了物料自聚反应 → 反应放热 → 压力飙升 → 最终超过设备极限爆炸。这是一个多步的因果传播链。但在实际的非结构化报告里，这七步可能分散在不同的段落里，甚至不同的报告中。

纯 LLM 的文本生成是逐 token 预测，它很容易跳过中间环节。你问它"冷却水循环泵故障怎么导致爆炸"，它有可能直接回答"泵故障导致爆炸"，中间的温度变化、化学反应、压力累积全被跳过了。我们实际测试中也验证了这一点——图谱里只有泵故障到温度上升这一步有明确的因果记录，后面的链条在已有数据中不完整。但系统的回答做到了诚实：它明确说了目前只能确认这一步，无法完整回答，然后基于现有信息和物性数据给出了安全建议。这个诚实性，恰恰是我们选 Graph RAG 而不是纯 LLM 的原因——LLM 大概率不会说"我不知道"。

## 为什么要用知识图谱：一个类比

【这是回应老师关于 KG 必要性问题的核心段落】

我想用一个类比来解释为什么我们选了"知识图谱 + LLM"这条路，而不是直接用 LLM 端到端。

假设你们系里有一位同学，他从来没学过化学工程基础。现在你给他一本化工原理教材，然后问他："精馏塔的进料温度升高了 15 度，会对塔顶产品的纯度有什么影响？"

他有两种方式回答。

第一种——他把教材从头读到尾，试着理解里面的内容，然后给出答案。这就是纯 LLM 的方式。他可能给出一个答案——"会影响纯度"——听起来没错，但他解释不了到底通过什么机制影响的，因为他没有真正理解精馏的过程。

第二种——你先帮他把教材的知识整理成一张图：精馏塔是一个节点，进料温度是一个节点，塔顶产品纯度是一个节点。它们之间有一条带箭头的线——"进料温度升高 → 再沸器负荷增加 → 上升蒸气量变大 → 塔顶馏出物中重组分夹带增多 → 塔顶产品纯度下降"。每条线都是明确的因果步骤。然后你再让他基于这张图回答问题。这就是 Graph RAG 的方式。

他要做的不是"猜一个答案"，而是"沿着图上的路径走一遍"。图的路径已经精确锚定了每一步的因果关系，LLM 只需要用自然语言把它表述出来。这样生成的答案，每一步都是可追溯、可验证的。

学术界对知识图谱在 LLM 时代是否还有必要，确实存在争议。2024 年微软开源 GraphRAG 之后，这个问题的讨论更加激烈。一些观点认为大模型可以直接对文档做问答，不需要先建图。但微软自己的实践和社区的大量验证表明：当问题是**关系型的、多跳的、需要精确约束**的时候，只有图谱能提供这种结构化的推理骨架。我们的领域——化工安全事故的因果链分析——恰好就是这种"需要精确约束的多跳关系推理"问题。

另外，我们刚刚做完实验，用同样的问题测试了纯 DeepSeek 和我们的 Graph RAG 系统。以"焊接火花有什么危害"为例——纯 LLM 给出的回答是概括性的，罗列了焊接安全的一些通用原则。但基于图谱生成的回答精确到了某一起具体事故的因果链——"焊接火花引燃了分流槽内的易燃物，火势蔓延到了相邻的污水处理池，引爆了池中积累的乙烯基乙炔、乙醛、乙炔"。同时图谱里还有另一条从焊接火花出发的路径——指向了 2014 年四川广元天森煤化的事故。这是纯 LLM 不可能做到的——因为它不知道这 30 份报告里具体哪一份提到了焊接火花。

更关键的是诚实性。我们问"氮气会导致窒息吗"，图谱里只有 1 条路径且是自循环——信息不够。系统老老实实回答"无法基于现有路径确定窒息的触发条件"，然后基于氮气物性给了通用建议。纯 LLM 面对同样的问题，大概率会基于常识编出一段关于氮气窒息的解释。在安全领域，"不知道的时候不乱说"比"什么都会说"要重要得多。

## 真实用户与价值

【回应老师关于"找真实用户"的建议】

我们也思考了这个项目能为谁提供价值。

最直接的用户是**化工专业的学生**——包括我们自己。我们有一门课叫化工安全工程，每学期都要做大量的案例分析。现在看案例的方式就是读 PDF 报告，几十页读下来很累，而且很难跨案例对比。"历史上类似工艺的类似事故有哪些？"目前只能靠记忆。如果我们的系统能建成，学生就可以用自然语言来查——不用知道事故名称和编号，就问一句"反应釜超温会引发哪些事故"，系统就能从多份报告中检索出相关案例并给出因果链。这对学习的效率提升是巨大的。

长期来看，一线安全管理人员的 HAZOP 分析、开工前安全审查、应急预案编制，都有可能用到这种知识检索能力。

当然，我们目前离"真实用户持续使用"还有距离。中期阶段我们能交付的是一个技术验证型的原型系统——证明管线能跑通、知识图谱能构建、问答能给出可追溯的因果回答。后期我们会尝试让几位正在上化工安全工程课的同学试用，收集反馈。

## 时间分配建议

- 博帕尔事故引入：1 min
- 问题规模 + 数据现状：1.5 min
- 三个致命缺陷：2.5 min
- 类比解释 + 回应 KG 质疑：2.5 min
- 真实用户 + 价值：0.5 min
- **合计：约 8 min**
