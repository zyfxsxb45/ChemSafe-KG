前面翟彝凡讲了为什么要做。我来回答另一个问题——这个问题之前有人做过吗？做过的人遇到了什么问题？我们做的事情和他们的区别在哪？

我把现有工作分成了三条技术路线，按从传统到先进的顺序来讲。每一条我都说清楚它的核心方法、代表工作、以及它的硬伤在哪。

## 路线一：传统的统计分析

最早的研究方法非常朴素——拿到一堆事故记录，统计事故类型、发生时间、涉及化学品、伤亡人数，然后画分布图。2007 年，关文玲和蒋军成在《中国安全科学学报》上发表了一篇论文，系统统计了 2001 到 2006 年中国化工企业的火灾爆炸事故。他们发现事故高发的设备类型是反应釜和储罐，高发化学品是苯类和氯气。这篇论文到今天引用了几百次，在化工安全领域很经典。

【翻到对比表】

这类方法的优点是简单直观，适合监管部门做宏观风险识别。但它的局限也很明显。它只能告诉你"什么设备出了多少次事"，不能告诉你"这个设备是怎么出的事"——因为它在统计高频共现，不在追踪因果传播。

而且它严重依赖结构化字段。一份事故报告里最有价值的内容——"事故的直接原因是脱丙烷塔的输气管线发生腐蚀，30 秒内释放了 7700 公斤烃类蒸气"——这段话如果不被录入到结构化字段里，统计分析就完全用不到它。

## 路线二：知识图谱的工业化尝试

大约从 2018 年开始，化工安全领域开始有人用知识图谱的思路来做事故分析。一篇硕士学位论文专门研究了"基于常见化工安全事故调查报告的事理图谱构建方法"——事理图谱是知识图谱的一个分支，重点不是静态的知识（比如苯的沸点是多少度），而是动态的事件之间的因果演化关系（比如苯泄漏导致了中毒）。

这个方向的思路是对的。但有一个根本问题一直没解决——图谱怎么建？现有的方法主要靠人工编写规则和手动标注。比如"如果报告里出现了'爆炸'和'温度升高'，就在这两个实体之间建一条关系"。规则写起来容易，但写全很难。化工事故类型太多，每类事故的因果链都不一样，靠人工规则很难覆盖。而且一旦想扩展数据源——比如加入新的年份或者新的化学品——规则又要重新调。

所以知识图谱方向最大的痛点是**构建成本**。图谱质量很高，但建图太慢、太贵、太依赖人。

## 路线三：LLM + Graph RAG 的最新范式

最近两年出现了一个新方向——用 LLM 来自动构建知识图谱。

微软 2024 年 7 月开源了 GraphRAG，核心理念是从非结构化文本中自动提取实体和关系，用社区发现算法做信息聚合。这个工具出来后，工业界大量落地了基于知识图谱的企业知识库问答系统。

在我们化工安全这个具体领域，2026 年初有一篇发在 Expert Systems with Applications 上的论文叫 GRAG-ProSafe QAS。他们的路线和我们非常接近——用 LLM 从事故报告中抽取实体和关系，构建知识图谱，然后在图谱上做问答。他们在 198 份钢铁行业事故报告上做了实验，构建了 1637 个节点和 2285 条边的图谱。在爆炸事故的多轮问答场景中，系统的忠实度、答案相关性和事实正确性都达到了比较高的分数。

这个工作给了我们很重要的参考——证明了用 LLM 自动构建化工安全知识图谱是可行的。但它也有几个没解决的问题。第一，它是针对钢铁行业的，不是我们关心的化工大安全领域。第二，它用的是英文报告，而我们做的是中文化工事故场景。第三，也是最重要的——它没有系统性地评估 LLM 抽取的准确率，也没有和纯 LLM 方案做过严格的对比实验。

## 我们的两个推进

基于上面三条路线的分析，我们做了两个方面的推进。

首先，我们针对中文化工安全场景设计了一套 Prompt Chain 策略。System Prompt 设定了化工过程安全专家的角色，实体类型和关系类型基于化工事故的领域知识做专门定义——比如 Equipment、Material、Abnormal_Condition、Consequence、Mitigation 这五种实体类型，以及 leads_to、involves、mitigated_by 这三种关系类型。这是针对化工事故因果链特点做的定制，不是通用的实体关系抽取模板。

其次，我们实现了从数据采集到问答交互的端到端自动化。从应急管理部官网爬取 HTML → 逐页解析事故文本 → LLM 批量抽取实体关系 → 写入 Neo4j 图数据库 → 通过 Streamlit 提供自然语言问答——这条管线全部是代码自动完成的，不需要人工标注。

## 回应老师的问题：知识图谱到底必不必要

【这是关键段落，老师开题时专门提了这个问题】

我在调研中对这个问题做了很多思考。学术界的争论是真实的——在大模型面前，知识图谱到底还值不值得建？有一种观点认为，大模型直接对文档做问答就行，建图的开销太大，性价比不高。

我们的初步结论是：**在化工安全事故的因果推理场景中，知识图谱是必要的，但必要性来自问题的性质，不是来自技术偏好。**

我举一个具体的例子。我们的库里目前有 30 份事故报告。用户问："焊接火花在化工事故中有什么危害？"

纯 LLM 看到这 30 份报告后，大概率给出一个通用回答——焊接火花温度高、能引燃可燃物、需要动火审批。这个回答有没有错？没有。但它从哪份报告里来的？不知道。

向量 RAG 会做 embedding 检索，找回和"焊接火花"语义最近的文本片段。但"焊接火花引燃分流槽内易燃物导致污水处理池爆炸"这段描述，和"电弧焊机火星掉入沉淀池引爆油气混合物"这段描述，在语义上并不相近——一个是分流槽，一个是沉淀池；一个是化工总厂，一个是煤化公司。向量检索很可能只找回其中一段，丢掉另一段。

Graph RAG 先建了图谱。焊接火花这个实体节点在 Neo4j 里连着多条 leads_to 关系——分别指向重庆长寿化工总厂 1987 年事故和四川广元天森煤化 2014 年事故。两起事故相隔 27 年、相距几百公里，但因为都涉及'火花引燃可燃物导致爆炸'这条因果链，被图谱关联在了一起。当用户问这个问题时，系统沿着所有关系检索到多条因果链，答案不仅包括"分流槽内乙烯基乙炔、乙醛、乙炔爆炸"，还包括预防措施和详细的物性数据。

这就是图谱的价值——它不用"语义相似"来判断，而是用"关系结构"来关联。两段文字可以语义上完全不相似，但只要它们描述的是同一类因果模式，在图谱里就是连在一起的。

我们再拿另一个问题来对比诚实性。"氮气会导致窒息吗"——图谱里只有一条自循环路径，信息不够。系统的回答第一句话就是"无法完整展现从氮气释放到工人呼吸衰竭的完整链条"，然后诚实地说"无法基于现有路径确定窒息的触发条件"。但同时，系统也没有完全不作为——它引用了氮气密度、氧气安全阈值这些物性数据，给出了通风检测和个体防护的通用建议。

如果纯 LLM 面对同样的问题，它不会说"我不知道"——它一定会生成一个看起来合理的回答，但那个回答里有多少是这 30 份报告里真正存在的知识，有多少是模型自己编的，你分不出来。

所以我们的回答是：在需要跨文档多跳推理、需要精确因果约束、需要可追溯来源、需要"不知道就承认不知道"的场景中，纯 LLM 和向量 RAG 都有盲点。图谱是一种结构化的补偿。构建成本更高，但安全领域的准确性和诚实性，值得这个成本。
