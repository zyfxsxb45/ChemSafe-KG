## 3.1 系统架构总览（2 min · A）

A：「前面两位讲了为什么做、别人怎么做的。接下来我告诉大家我们到底做了什么。」

【翻到架构图】

「这是我们系统的五层架构。从下往上看：

最下面一层是数据获取与预处理。我们做了三件事——第一是从应急管理部官网爬取事故报告；第二是接入了 PubChem 化学品物性 API；第三是接入了 Open-Meteo 全球气象数据 API。

往上一层是 LLM 知识抽取。这是我们整个项目的技术核心。我们设计了一套 Prompt Chain，让 DeepSeek 大模型作为化工安全专家，从非结构化的事故报告中提取实体和因果关系。

再往上一层是知识存储。抽取出来的结构化数据——实体节点和因果关系的边——存入 Neo4j 图数据库。同时事故主表和化学品物性表存在 SQLite 里。

再往上是 Graph RAG 检索。用户提问的时候，系统先从问题里识别出关键实体，然后在 Neo4j 里查找从这个实体出发的所有因果路径。

最上面一层是问答生成和前端展示。检索到的因果路径作为约束上下文输入给 LLM，LLM 生成回答，通过 Streamlit 网页展示给用户。

我按模块说一下完成情况。截止到第 13 周，12 个核心模块中 10 个已经完成。完成的意思是代码可用、管线跑通、有实际数据验证。两个还没做完的——PDF 解析和多源数据融合——我们放在后续三周补上。」

## 3.2 数据采集（3 min · B）

B：「我来补充数据采集这一层。」

【翻到数据采集页】

「先说数据源的选择。我们一开始的目标数据源是 ciedu.com.cn，化工安全教育公共服务平台。这是一个非常理想的 P0 源——它系统地整理了过去几十年的事故调查报告原文，每个事故条目都有独立的文章页和 PDF 附件下载。但 requests 请求被拦，一直返回 502。

后来我们做了一个重要的发现——这个网站用浏览器的无头模式可以正常访问。它分年份组织内容，从 1950 年一直到 2026 年，覆盖的高危化学品事故案例数量远超我们最初预估。不过它有一套人机验证的反爬机制，用程序直接请求行不通，需要借助浏览器的自动化工具来采集。

对于我们目前的课程项目，要在中期阶段交付一个稳定可用、数据量也够的知识图谱，我们选择了一个更务实的方案——先把应急管理部官网『历史上的危化品事故』栏目作为主数据源。这个源虽然每条事故报告只有几百字，不是完整的调查报告原文，但它胜在系统性强、涵盖范围广、结构稳定。每个月一期刊出，从 2018 年到现在累计 94 期，每期 17 到 41 起事故。每一起都有事故发生日期、地点、伤亡人数和根因分析。根因分析是 LLM 抽取因果链最关键的信息。

我们来具体讲爬虫是怎么实现的。」

【翻到爬虫实现细节页】

「爬虫分了几个层次。首先从列表页出发——列表页有 5 页，URL 规律很简单：第一页没有编号，第二到第五页是 index_1 到 index_4。我们发现了一些细节上的坑——列表页里给出的链接是用相对路径的，比如 `../202604/t20260430_602285.shtml`，直接拼字符串会出错。我们用 `urljoin()` 来正确处理相对路径的解析。

然后是月度详情页的解析。这是整个爬虫最花时间的部分。应急管理部的月度页面每期都按同样的格式组织——先是"国内事故"，按石油化工、煤化工、精细化工等等分类；然后是"国外事故"。每条事故有一个标题行，紧跟着一段描述文字。

我们最开始猜测事故标题是用 `<strong>` 标签包裹的。写了解析器后发现不对——strong 标签只用在章节标题和分类标题上。真正的事故标题是纯文本的 `<p>` 元素。怎么区分它和描述段落？我们观察了几个规律：事故标题的长度在 13 到 45 个字符之间，而且一定包含"事故"、"爆炸"、"泄漏"、"火灾"、"中毒"这些关键词之一。描述段落通常在 80 个字符以上，而且往往以年份开头，或者包含"事故直接原因是"。

解析结果保存为单独的 `.txt` 文件——文件名就是事故标题，内容包含了标题、来源、日期和完整描述。所有文件 UTF-8 编码，命名用的是纯文本，避免了 Windows 文件名的非法字符问题。除了存 TXT，我们还把每条事故的基本信息和 LLM 抽取结果同步写入 SQLite 关系数据库——`AccidentRecord` 表格包含 `root_cause`（根原因）、`consequence`（后果总结）、`related_chemicals`（涉及化学品）、`related_equipment`（涉及设备）四个 LLM 自动填充的结构化字段。这就把非结构化文本自动映射成了可做 SQL 查询的结构化数据。

除了事故文本，我们还做了两个辅助数据源的 API 接入。PubChem 化学品物性数据库——它是全球最大的免费化学品数据库，REST API 不需要 Key，我们集成了 20 种常见高危化学品的物性数据，包括分子量、沸点、闪点这些参数。Open-Meteo 气象数据——同样不需要 Key，全球覆盖，可以回溯到 1940 年。这两个数据源目前是独立采集的，后续会和事故数据做关联分析。」

## 3.3 课程联系：用学过的工具做了什么

B：「我顺带说一下这个项目用到了哪些课程里学过的技术。化学品物性表是一个 Pandas DataFrame，列的格式和课程讲的一样——我们用它来构建化学品物性数据表。

事故主表是 SQLAlchemy ORM 管理的，model 定义跟数据库实验课学的 SQL 建表思路是一样的，只是我们用了 Python ORM 而不是手写 SQL。图存储用的是 Neo4j 和 Cypher 查询语言。知识图谱问答的本质是让 Cypher 做变长路径查询，然后拿到结果再发给 LLM。」

## 3.4 LLM 知识抽取（2 min · A）

A：「回到我来讲技术核心部分——LLM 知识抽取。」

【翻到 Prompt Chain 页】

「这个环节我们需要一个通用大模型像一个化工安全专家一样阅读事故报告并提取知识。怎么让模型做到这点？核心是靠 Prompt Chain。

我们设计的 System Prompt 是这样开头的——"你是一位化工过程安全专家"。这不是随便写的，我们在文献里看到，设定专业角色可以显著提高 LLM 对专业文本的理解精度。

然后我们定义了五种实体类型。为什么要自己定义，而不是让 LLM 自由发挥？因为如果让 LLM 随意抽取，它可能造出几十种类型，很多写得不一致的——同一个设备在这一段里叫"反应器"，在下一段里叫"反应釜"。不一致的实体类型入库后会严重影响图谱的查询和推理。所以我们用预定义的 Schema 做强约束。

同样地，关系也只有三种：leads_to 因果关系、involves 涉及关系、mitigated_by 缓解关系。我们刻意保持关系类型很少，因为少意味着图结构的可遍历性好——你再复杂的因果链，在 Neo4j 里无非就是一条 leads_to 路径的变长匹配。

输出格式用 JSON Schema 约束。这是关键的一步——LLM 有时候会自由发挥输出格式，加一个 `"event_description": "..."` 这种我们没定义过的字段，或者漏掉 `"root_cause"`。JSON mode + Schema 约束把这个不确定性控到了最低。

技术上我们还做了几个配置。温度参数设为 0.1——温度越低，输出的确定性越高，适合知识抽取任务。最大 token 数设到 4096，给长文本抽取留足空间。有 3 次自动重试——如果 API 临时波动，指数退避重试。

抽取完之后走三层验证。第一层验证结构的完整性——event_chain、root_cause、consequence 三个字段都必须在。第二层验证类型合法性——实体类型必须是预定义的五种之一。第三层计算置信度评分——链越长、信息越完整，分数越高。

我们用 30 条真实事故做了一个测试。每条事故平均抽取 5 到 6 条因果关系。30 条事故一共提取了 162 条关系，全部成功入库，没有结构错误导致的写入失败。当然，这个抽取质量还需要用更大的数据量和人工标注来做正式评估，我们会在接下来的数据扩充阶段做这个。」

## 3.5 知识图谱与问答（2.5 min · C）

C：「A 和 B 讲了怎么把数据拿到、怎么从文本里抽出知识。我来补充知识是怎么存进去的，以及存进去之后能回答什么问题。」

【翻到 Neo4j 状态页】

「目前知识图谱里有 212 个实体节点和 162 条因果关系边，来自 30 条入库的事故。实体覆盖了五大类型。

关键的细节是，这些节点和边不是孤立的一条一条，而是一个跨事故关联的网络。举个例子——图谱里有一个节点叫"焊接火花"。这个节点连接了两起不同事故的因果链。一起是 1987 年重庆长寿化工总厂的爆炸——焊接火花引燃了分流槽内的易燃物，导致污水处理池里的乙烯基乙炔、乙醛、乙炔混合气体爆炸。另一起是 2014 年四川广元天森煤化的爆炸——电弧焊机的火星从沉淀池观察孔掉入池内，引燃油气混合物导致爆炸。

两起事故时间相差 27 年、地点相差几百公里，但在图谱里通过同一个点火源类型节点被关联在一起。这就是知识图谱比孤立文本分析强的关键——它可以跨越时间和空间的差异，找出事故之间的共性规律。

节点去重是怎么做的？我们用 Neo4j 的 MERGE 操作，而不是 CREATE。MERGE 等价于 Cypher 的 MERGE 语义——先按 name 属性查找已存在的节点，有就复用，没有才创建。同时对 Equipment 和 Material 类型创建了 UNIQUE 约束，双重保障。

批量入库用的是 `run_extraction_pipeline.py` 这个脚本。它做三件事——读取 `data/raw/accident_reports/` 下的所有 txt 文件，去掉文件头的元信息，然后把事故描述文本发给 LLM 抽取，最后把抽取的三元组写入 Neo4j。每 5 份报告写一次，减少连接开销。跑完 30 份事故大概需要 5 分钟。」

【翻到问答演示页】

「最后我展示一下问答效果。我们用同样的 6 个问题，跑了纯 DeepSeek 和我们的 Graph RAG 系统两轮。以下是实际的输出结果。」

「先说效果最好的两个。」

「**静电火花在化工中有什么危险？**系统从图谱里检索到 8 条因果路径，给出了一个很完整的回答。因果链条是——静电火花直接导致爆炸，爆炸进一步引发了多起严重后果：3 人死亡、6 人死亡这两种不同事故里的人员伤亡，还有房屋和汽车烧毁的财产损失、罐内气体和残留液体的二次爆炸燃烧，以及居民疏散。而且图谱里明确记录了缓解措施——泡沫灭火系统和罐区喷淋可以控制爆炸后的火灾蔓延。一条问题把点火源到后果到措施的完整链条全拉出来了，这是 8 条路径跨事故交叉检索的结果。」

「**苯大量泄漏有什么后果？**系统检索到 6 条路径，给出了两条并行的因果链。第一条链——苯大量泄漏形成高浓度苯蒸气云团，吸入导致急性苯中毒。第二条链——苯大量泄漏直接引发火灾，火灾造成 4 人死亡。系统还引用了苯的物性数据——苯的沸点 80 度，蒸气密度是空气的 2.77 倍，所以泄漏后会在低洼处积聚形成高浓度蒸气。另外还提到了应急措施——救援人员关闭泄漏阀门可以阻止中毒恶化。」

「**焊接火花有什么危害？**检索到 5 条路径。系统精准定位了具体的事故场景——焊接火花引燃分流槽内的易燃物，火势蔓延到相邻的污水处理池，引爆了池中积累的乙烯基乙炔、乙醛、乙炔这些易燃气体。系统还给出了这些气体的爆炸极限数据，并且强调了严格的动火作业管理措施。这个回答的一个关键特点是——它定位到了一起具体事故的详细因果链，不是泛泛地说"焊接火花危险"。」

「**液氯泄漏有什么危险？**检索到 2 条路径。系统给出了液氯大量泄漏导致人员伤亡、进而引发居民疏散的链条。虽然没有非常多的层次，但至少事实是精确的——不是泛泛地说液氯有毒，而是明确讲泄漏导致伤亡再到疏散。这和纯 LLM 的"液氯泄漏会造成中毒"不一样——纯 LLM 可能给一个很长的答案，但哪一句来自哪份事故报告？不知道。我们的答案里每一步都有图谱节点作为来源。」

「然后说两个不那么完美的，但这反而是我们想展示的。」

「第一个——**冷却水循环泵故障如何导致丙烯腈储罐爆炸？**这是开题报告里作为样本的问题。实际检索结果只有 1 步因果路径——泵故障导致储罐温度持续上升。后面的"温度上升如何导致爆炸"在图谱里没有找到路径。系统的回答非常诚实——先明确展示这一步路径，然后说"信息局限性：检索到的因果路径仅建立了泵故障到温度持续上升这一事实，未提供温度上升如何进一步导致爆炸的因果链，因此无法完整回答"。然后基于丙烯腈的物性给出了安全建议。

这不是系统不行。这是我们当前 30 条事故的数据量决定的——这条因果链在已有的 30 条事故里恰好没有完整的记录。但这个回答本身——坦承信息不足，不乱编——恰恰是我们想要的设计效果。」

「第二个——**氮气会导致窒息吗？**检索结果只有一个长度为 1 的自循环路径——'工人氮气窒息 leads_to 工人氮气窒息'。这其实就是图谱里只有一个节点，没有前因后果。系统的回答是——先说明这个路径"无法完整展现从氮气释放到工人呼吸衰竭的完整链条，缺少氮气泄漏源、空间氧气浓度下降、工人进入缺氧区域等环节"，然后诚实地说"无法基于现有路径确定窒息的触发条件"。但同时，系统也没有完全不作为——它基于氮气的物性数据给出了一些通用的安全建议。

我展示这个例子是想说一个设计理念——在安全关键领域，"不知道"比"乱猜"更有价值。纯 LLM 面对这个问题，可能会根据常识编一个看起来合理的答案。我们的系统选择了说"我查了，图谱里没有足够的信息"。这对实际应用来说是一种负责任的行为。」

「总结一下：静电火花、苯泄漏、焊接火花、液氯泄漏这四个问题回答质量很好；泵故障问题因为数据量不够，路径不完整但系统诚实告知；氮气窒息问题图里没有足够信息，系统宁愿说不知道也不编造。这些结果验证了我们最初的假设——图谱约束可以有效防止 LLM 在多跳因果推理中的幻觉。」
