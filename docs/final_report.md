**ChemSafe-KG：基于大模型驱动的化工安全事故知识图谱构建与因果推理问答系统**

---

## 二、研究动机与背景

### 2.1 问题背景

化工安全事故的分析与预防是过程安全领域的核心议题。应急管理部数据显示，仅 2023 年全国就发生化工事故 120 余起，造成重大人员伤亡和经济损失。每一起事故调查报告都蕴含宝贵的经验教训——事故链条中的设备故障路径、操作失误模式、应急响应盲区，这些知识如果能够被系统性地提取、关联和复用，将直接服务于安全培训、风险预警和工艺优化。

然而，这些知识长期以非结构化 PDF 和 HTML 文本形式分散存储在各级应急管理部门网站中，难以被高效检索、关联分析与复用。安全管理人员查阅一起事故需要翻阅数十页报告，横向对比多起事故的共性致因则几乎不可能。

### 2.2 纯 LLM 方案的局限

随着大语言模型（LLM）能力的飞速提升，研究者尝试直接利用 GPT-4、DeepSeek 等通用模型回答化工安全领域的专业问题。但实践表明，纯 LLM 方案存在三个致命缺陷：

- **领域幻觉**：对"光气化反应釜尾气破坏器联锁摘除"等专业术语，模型倾向于字面拆解与臆测，缺乏对化工过程因果逻辑的精确把握。
- **知识时效性断层**：模型训练数据截止于特定时间点，无法覆盖最新发生的具体事故案例。
- **多跳逻辑断裂**：事故致因往往涉及"设备→物料→异常状态→后果"的多步传播链条（通常 3-7 步），纯文本生成容易跳过中间环节，输出"看似合理但因果倒置"的答案。

### 2.3 相关工作

近年来，Graph RAG（图检索增强生成）技术成为解决上述瓶颈的主流范式。Microsoft Research 的 GraphRAG 框架（Edge et al., 2024）提出用知识图谱提供精确的领域事实与逻辑骨架，由 LLM 负责自然语言理解与生成。在化工安全领域，CSB（美国化学品安全委员会）的事故调查方法论强调因果链分析，但尚未与自动化 KG 构建技术结合。

传统知识图谱构建依赖人工规则与大量标注，难以规模化。本项目提出的核心创新在于：**以 LLM 自身作为知识抽取引擎**，设计 Prompt Chain 策略从非结构化事故报告中自动化构建因果知识图谱，并在此基础上实现因果约束的 Graph RAG 问答系统。

## 三、问题定义与挑战

### 3.1 核心研究问题

本项目试图回答三个核心问题：

1. **LLM 驱动的自动化 KG 构建**：如何设计有效的 Prompt Chain 策略，使通用大模型能够从非结构化事故调查报告中准确抽取实体（设备、物料、异常状态、事故后果、应急措施）及其因果传播关系，并以结构化图数据形式存储？

2. **因果约束的 Graph RAG 问答**：如何利用知识图谱中的因果链路约束大模型的生成空间，使问答结果严格遵循化工过程的物理逻辑，避免幻觉与逻辑跳跃，且每条陈述可追溯到具体的因果路径来源？

3. **多源数据融合分析**：如何将事故案例数据与化学品物性数据库、气象环境数据关联融合，构建多维事故风险画像？

### 3.2 难点挑战

- **非结构化文本的因果抽取**：事故报告中的因果链往往隐含在叙述中，需要模型理解"因为 A 故障导致 B 超温，B 超温引发 C 分解，C 分解产生 D 气体，D 气体遇 E 火花发生爆炸"这类多跳因果推理。
- **实体类型约束**：化工安全领域有严格的实体分类体系（设备、物料、异常状态、后果、措施），必须约束 LLM 在此框架内进行抽取，不得产生未定义的实体类型。
- **因果方向性保证**：后果不能出现在原因之前。这看似显然，但在文本顺序与因果顺序不一致时（如倒叙描述），LLM 容易出错。
- **答案可信度**：在安全领域，编造的代价极高。必须建立从答案陈述到 KG 路径的可追溯机制。

## 四、解决方法

### 4.1 五层系统架构

```
Streamlit Web 应用层 (问答 + 可视化 + 管理)
┃  Graph RAG 问答层 (因果约束 LLM 生成 + 来源引用)
┃  知识存储层 (Neo4j 5.26.25 + SQLite + 4索引 + 分析视图)
┃  LLM 知识抽取层 (DeepSeek deepseek-v4-flash + Prompt Chain)
┃  数据获取与预处理层 (爬虫 + 文本清洗 + 多源融合)
```

### 4.2 Prompt Chain 知识抽取（核心创新）

我们设计了一套严格的 Prompt Chain 策略驱动 DeepSeek deepseek-v4-flash 进行结构化抽取：

**System Prompt** 定义化工过程安全专家角色，规定 5 种实体类型（Equipment、Material、Abnormal_Condition、Consequence、Mitigation）和 3 种关系类型（leads_to、involves、mitigated_by），并附 5 条抽取规则：因果顺序排列、完整链条抽取（至少 3 步）、伤亡概括化、忠实于原文、实体名一致性。

**Few-shot 示例** 提供一个完整的"丙烯腈储罐爆炸"案例抽取模板，展示从设备故障→5 步异常状态→事故后果→应急措施的完整链条，标注正确与错误做法。

**输出格式** 约束为严格的 JSON Schema：`{event_chain: [...], root_cause: str, consequence: str}`，利用 DeepSeek 的 JSON Mode 确保格式一致性。

### 4.3 因果约束的 Graph RAG 问答

三层实体匹配策略确保用户问题中的实体能准确对齐到 KG 节点：

1. **精确匹配**：`n.name = query` (score=3)
2. **包含匹配**：`n.name CONTAINS query` (score=2)  
3. **语义嵌入匹配**：基于 sentence-transformers (MiniLM-L12-v2) 的余弦相似度匹配，解决"液氯→氯气""高温→温度升高"等词法盲区

检索到因果路径后，ContextBuilder 构建 Graph RAG 系统 Prompt，要求 LLM 严格按照检索路径回答、标注每条陈述的来源路径编号 `[路径N]`、不得添加路径外内容。当路径与问题不相关时，LLM 必须回答"无法回答"而非编造。

### 4.4 多源数据融合

DataMerger 模块实现三层融合：事故文本中提取化学品名与 chemical_properties 表关联、事故日期地点与 weather_records 表关联、Neo4j Material 节点补充物化性质。最终产出统一分析视图（200 行 × 19 列）。

## 五、数据流水线

### 5.1 数据采集

| 数据源 | 技术 | 数据量 |
|--------|------|--------|
| mem.gov.cn 应急管理部 | requests + BeautifulSoup，95 个月度页解析 | 200 份事故报告 |
| PubChem 化学品物性 | pubchempy 库，29 种危化品 | 100% 含分子量/CAS/IUPAC |
| Open-Meteo 气象 | 免费 Archive API，34 省坐标 | 8 条历史天气记录 |

爬虫逐段扫描月度汇编页的 HTML 结构，用章节标题（strong 标签）、分类标题（短文本）、事故标题（13-45 字符含关键词）、描述文本的特征区分四类元素，提取每起独立事故。CSB 数据源通过 CSS 选择器匹配调查卡片。

### 5.2 LLM 知识抽取

`run_extraction_pipeline.py` 批量处理 200 份 .txt 报告：读取→清洗→调用 DeepSeek→JSON 解析→三元组转换→每 5 条批量 MERGE 写入 Neo4j + INSERT 写入 SQLite。抽取结果经 ResultValidator 校验 JSON 结构完整性和实体类型合法性。

### 5.3 知识存储

双存储架构：Neo4j 存储实体关系图（6 节点类型 + 3 关系类型 + UNIQUE 约束），SQLite 存储结构化数据（3 表 + 4 索引 + 1 分析视图 `accident_chemical_view`）。

### 5.4 统一编排

`pipeline.py` CLI 工具支持分阶段执行：`acquisition`（采集）、`extraction`（抽取）、`enrich`（充实）、`qa`（验证），可断点续跑。

## 六、实验分析

### 6.1 LLM 抽取质量评估

我们对 200 份 mem.gov.cn 事故报告进行全量抽取，结果如下：

| 指标 | 数值 |
|------|------|
| 处理报告总数 | 200 |
| 成功抽取 | 174 (87.0%) |
| 失败（JSON 解析错误） | 26 (13.0%) |
| 抽取三元组总数 | 995 |
| 平均三元组/报告 | 5.7 |
| 实体类型覆盖 | Equipment 166 / Material 107 / Abnormal_Condition 1,076 / Consequence 185 / Mitigation 4 |

**失败分析**：26 份失败的报告中，LLM 返回了空响应或非标准 JSON（如多行 JSON 被 Markdown 代码块包裹）。这主要是因为部分报告文本极短（<100 字符），LLM 难以从有限信息中抽取完整因果链。

**Mitigation 偏少分析**：应急措施仅 4 条，根因在于 mem.gov.cn 月度简报的数据特性——这种简报以"警示信息"为定位，重点描述事故经过和原因，极少提及应急处理措施。完整的事故调查报告（如 ciedu.com.cn 上的 PDF）会包含详细的应急响应章节，将是后续数据源扩展的重点方向。

### 6.2 问答质量评估

我们对系统进行了 6 组覆盖不同因果模式的问答测试：

| 问题 | 检索路径数 | 来源引用 | 回答长度 |
|------|-----------|---------|---------|
| 有限空间作业导致中毒窒息的常见原因？ | 109 | ✓ [路径N] | 1,049 字 |
| 反应釜爆炸通常由哪些因素引发？ | 154 | ✓ | 1,281 字 |
| 储罐泄漏事故中哪些设备故障最常见？ | 16 | ✓ | 839 字 |
| 硫化氢中毒事故的典型因果链？ | 190 | ✓ | 1,248 字 |
| 盲目施救如何导致事故后果扩大？ | 124 | ✓ | 1,583 字 |
| 违规操作在化工事故中扮演什么角色？ | 110 | ✓ | 950 字 |

**100% 的答案包含来源路径引用**，每条关键陈述可追溯到具体的 KG 因果链。

**幻觉对抗测试**：当问题超出 KG 覆盖范围（如"冷却水循环泵故障如何导致储罐爆炸"，KG 中无此实体），LLM 正确回答了"根据当前知识图谱，无法回答该问题"，且给出了具体原因（检索到的路径均与冷却水循环泵无关），而非编造内容。

### 6.3 关系数据库查询性能

SQLite 在 187 行数据上的 8 类分析查询均在 0.5-3.6ms 完成。日期索引将查询从 1.7ms 降至 1.0ms（1.7× 加速），受限于数据量级，加速比预期在小数据集上不显著。

### 6.4 图数据库查询性能

| 查询类型 | 耗时 |
|----------|------|
| 全节点计数 | 33.8ms |
| 按类型聚合 | 64.2ms |
| 因果路径 1 跳 | 61.7ms |
| 因果路径 3 跳 | 1,237.7ms |
| 全文搜索 | 54.1ms |

3 跳因果路径查询耗时较高（1.2s），原因是可变长路径 `[:leads_to*1..3]` 在图密度较高时存在组合爆炸。实际应用中通过限制返回路径数（LIMIT 50）和深度（max_depth=3）控制查询复杂度。对于更大规模图谱，可考虑 APOC 扩展库的路径算法优化。

### 6.5 数据完整率

- accidents 表核心字段：title 100%、date 99%、root_cause 100%、consequence 100%
- 关联字段：related_chemicals 39%、related_equipment 55%（取决于 LLM 是否能从短文本中识别）
- chemical_properties 表：100% 字段完整（5 字段全部有值）

## 七、数据产品

### 7.1 Streamlit Web 应用

最终交付的交互式 Web 应用包含 5 个功能页面：

- **系统概览**：实时 Neo4j 统计，五层架构图
- **因果推理问答**：自然语言输入→三层实体匹配→因果路径检索→Graph RAG 约束生成→答案+来源引用
- **多维数据分析**：4 标签页，10 种 Plotly 交互式图表（年份分布/月度趋势/事故类型饼图/化学品频次/设备频次/风险矩阵/节点类型分布/因果桑基图/地区分布/数据表）
- **知识图谱浏览**：streamlit-agraph 交互式全局图谱 + 因果路径探索（选实体→画路径有向图→文本详情）
- **系统管理**：数据流水线控制、数据库状态、配置检查清单

### 7.2 CLI 工具链

`pipeline.py` 提供完整的命令行操作接口，支持分阶段执行和断点续跑。`scripts/run_evaluation.py` 一键生成包含 SQL 查询结果、QA 测试报告、E/R 图、性能基准的综合评估报告。

## 八、经验与教训

### 8.1 技术阻碍与攻克

1. **爬虫反爬对抗**：ciedu.com.cn 的 CAPTCHA 机制导致 requests 返回 502 错误。转而聚焦 mem.gov.cn 作为主数据源，其 95 个月度汇编页无反爬限制，提供 2000+ 起事故的稳定来源。

2. **PubChem PUG REST API 格式变更**：原有的 API 端点格式全部返回 400 Bad Request。切换到 pubchempy Python 库，通过 Compound 对象直接访问物性字段，成功获取 29 种危化品数据。

3. **LLM JSON 输出不稳定**：约 13% 的报告抽取失败，主要是 LLM 返回空响应或被 Markdown 代码块包裹的非标准 JSON。通过在 JSON 解析前自动剥离 ```json...``` 标记缓解了部分问题，但仍需在 Prompt 层面进一步强化格式约束。

4. **Neo4j 数据隔离**：同一 Neo4j 实例中存在其他项目的节点。通过在 `get_all_entity_names()` 和 `get_entity_count()` 中添加标签过滤，以及执行 `DETACH DELETE` 清理外部节点，确保了 ChemSafe-KG 数据的纯净性。

### 8.2 经验总结

- **Graph RAG 的幻觉抑制效果显著**：严格约束 LLM 在检索到的因果路径内生成答案，并标注来源路径编号，是抑制幻觉的有效手段。实测中 LLM 能正确识别不相关问题并拒绝编造。
- **数据源选择决定知识图谱的上限**：mem.gov.cn 月度简报的"警示"定位决定了 Mitigation 节点稀缺。知识图谱的质量最终受限于数据源的信息丰富度。
- **双存储架构互补性强**：Neo4j 处理图遍历和路径查询，SQLite 处理结构化聚合和统计，两者各司其职，通过 DataMerger 的统一视图实现跨源分析。

## 九、项目总结

ChemSafe-KG 成功实现了一个端到端的化工安全事故知识图谱系统。核心成果包括：

1. **自动化 KG 构建**：设计 Prompt Chain 策略驱动 DeepSeek 从 200 份非结构化事故报告中抽取 995 条三元组，构建了包含 1,538 个节点和 1,727 条关系的因果知识图谱，抽取成功率 87%。

2. **因果约束 Graph RAG 问答**：三层实体匹配 + 因果路径检索 + 来源引用标注的问答流水线，在 6 组测试中 100% 产生带来源引用的回答，LLM 能正确识别超出 KG 范围的问题并拒答。

3. **多源数据融合**：整合事故报告、29 种化学品物性（PubChem）和历史气象数据（Open-Meteo），构建统一多维分析视图。

4. **完整的工程交付**：包括 Streamlit Web 应用（5 页面、10 种图表）、CLI 工具链（pipeline.py + 评估脚本）、Git 版本管理、框架文档和演示指南。

**未来工作方向**：接入 ciedu.com.cn 完整调查报告以提升 Mitigation 覆盖率；集成 PaddleOCR 处理扫描 PDF；添加异步并发抽取加速；部署 Docker 容器化环境。
