## 一、架构设计类

### Q1：为什么用 Neo4j 而不用 MySQL / PostgreSQL 来存知识图谱？

**回答人**：A 或 C

**核心思路**：关系型数据库擅长表格 JOIN，但不擅长变长路径遍历。

「这个选择的核心原因是查询模式不同。我们的核心查询不是"找到所有温度超过 200 度的反应釜"，而是"从一个故障节点出发，顺着 leads_to 关系，一路走到爆炸节点，中间的路径任意长"。

在 SQL 里，这个查询要写成多表自 JOIN——如果因果链有 5 步，就得 5 次 JOIN。而且你不知道用户的查询会有几步，只能写递归 CTE，执行效率很差。

在 Neo4j 的 Cypher 里，一句话搞定：`MATCH path = (start)-[:leads_to*1..6]->(end)`。星号表示变长路径匹配，引擎会用图遍历算法沿边扩展——这就是图数据库的索引结构天然擅长的事情。

当然，我们不是把所有数据都塞到 Neo4j 里。事故主表、化学品物性表、气象数据表这些用 SQLite 存——SQLAlchemy ORM 管理，和数据库课程里学的完全一致。」

### Q2：为什么不直接用向量 RAG，而要建图？

**回答人**：A

**核心思路**：向量 RAG = 几段相似文字；Graph RAG = 一条精确因果链。

「向量 RAG 能回答"这篇文档里说了什么"。但我们的用户问的是"冷却水循环泵故障怎么一步步导致爆炸"——这是多步因果逻辑，不是语义相似度能回答的。

用化工的类比——向量 RAG 像是拿着一份报告目录找"泵故障"这个词，把提到这个词的几段报告粘在一起给 LLM 看。Graph RAG 像是先把报告画成一张流程图——泵故障指向温度升高，温度升高指向自聚反应，自聚反应指向压力飙升，一直到爆炸——然后沿着这条流程图走一遍。

我们做的实验验证了这一点。同一个问题——"焊接火花有什么危害"——纯 LLM 只能给出通用安全回答。但 Graph RAG 在图谱里找到了 5 条因果路径，给出了具体事故场景——焊接火花引燃分流槽内的易燃物，蔓延到污水处理池引爆了乙烯基乙炔、乙醛、乙炔混合气体。回答里连这些气体的爆炸极限数据都引用了，还给出了动火作业管理的具体措施。

更关键的例子是"氮气会导致窒息吗"——图谱里只有一条自循环路径。系统没有硬编，诚实地回复"无法基于现有路径完整回答"，然后给出了基于氮气物性（密度 1.25 kg/m³，氧含量安全阈值 19.5%）的通用安全建议。LLM 面对同样的问题一定会生成一个看起来很合理的答案——但它不会告诉你"我没证据"。Graph RAG 会。这就是约束机制。」

## 二、爬虫实现类（B 重点准备）

### Q3：_parse_mem_list_pages() 是怎么从列表页提取月度链接的？

**回答人**：B

**核心代码逻辑**：

「这个方法分三步。第一步是构造 5 个列表页的 URL——第一个是 `/fw/jsxx/lssdwhpsg/`，后面四个是 `index_1.shtml` 到 `index_4.shtml`。

第二步是遍历 5 个页面，每个页面用 BeautifulSoup 解析，用 `soup.find_all("a", href=re.compile(r"t\d+_\d+\.shtml"))` 找所有文章链接。应急管理部每篇文章的 URL 有固定格式——比如 `t20260430_602285.shtml`——前缀是 t，后面是日期加数字编号。

第三步是用 `urljoin()` 处理相对路径。列表页 href 的值是 `../202604/t20260430_602285.shtml`，不能用简单拼接。urljoin 会自动把这个相对路径解析成完整的绝对路径 `https://www.mem.gov.cn/fw/jsxx/202604/t20260430_602285.shtml`。

返回的是一个 dict 列表，每个 dict 有 title、url、date、source 四个字段。」

### Q4：_extract_accidents_from_page() 怎么区分事故标题和分类标题？

**回答人**：B

**核心算法**：

「这是整个爬虫最关键的解析逻辑。mem.gov.cn 的月度页面结构非常规整——`div.cont` 里面全是 `<p>` 标签。

算法逐段遍历所有 `<p>`。三种情况要区分：

1. 章节标题：包裹在 `<strong>` 标签里，文本匹配"一、"、"（一）"、"2026年4月"这些正则模式。碰到就 flush 当前缓存的事故，然后跳过。

2. 分类标题：纯文本段落，长度不超过 7 个字符，且在预定义的分类集合里——石油化工、煤化工、精细化工、有机化工、无机化工、医药、化肥、农药、其他。碰到也 flush 跳过。

3. 事故标题：纯文本段落，长度在 13 到 45 个字符之间，包含"事故""爆炸""泄漏""火灾""中毒""爆燃""闪爆""窒息"这些关键词之一。碰到就 flush 当前事故，创建新的事故缓存。

4. 不符合以上三种的都是描述段落，追加到当前事故的文本缓存里。

最后 flush 一次，确保最后一个事故不丢失。」

### Q5：ciedu.com.cn 的具体情况是怎么回事？

**回答人**：B

「ciedu.com.cn 是化工出版社运营的化工安全教育公共服务平台。它的 `/article/category/accidents` 页面用浏览器可以正常访问，按年份列出事故调查报告，从 1950 年到 2026 年，每条都有原文链接和 PDF 下载。

但 requests 直接请求被挡，返回 502。我们把 User-Agent 改成浏览器的也不行。网站有一个 turnstile 人机验证机制。

所以当前对这个源的判断是：数据质量极高、覆盖范围超过 mem.gov.cn，但反爬严格。适合中期汇报后以 browser tool 的方式接入。目前不把它作为中期汇报的核心数据源，但不排除项目后期拿它来扩充 KG。」

## 三、LLM 抽取类（A 重点准备）

### Q6：extract_from_text() 的完整调用链路是怎样的？

**回答人**：A

**代码流程**：

「这个方法做了四件事。

第一步——生成 Prompt。从 PromptTemplates 中取 System Prompt 和抽取指令模板，把事故文本填入 `{report_text}` 占位符。System Prompt 扮演化工过程安全专家，定义了 5 种实体和 3 种关系。指令模板用 JSON Schema 约束输出。

第二步——调用 LLM。用 LLMClient.chat_json() 走 OpenAI SDK。这个方法的封装做了三件事——设置 `response_format={"type": "json_object"}` 让模型输出 json；用 temperature=0.1 保证低随机性；实现 3 次自动重试和指数退避。

第三步——解析 JSON。直接 `json.loads()` 解析 API 返回的 content。如果解析失败——比如模型偶尔在 JSON 外面包了 markdown 包裹符——会抛出异常并被上层捕获。

第四步——验证。ResultValidator 检查结构完整性、类型合法性和置信度。

返回的是一个 dict，包含 event_chain、root_cause、consequence 三个字段。」

---

### Q7：Prompt 模板为什么定义了 5 种实体而不是更多？

**回答人**：A

「这是一个刻意做减法而不是加法的设计决策。

化工领域的实体类型理论上可以定义很多种——阀门、管道、反应器、换热器、精馏塔等等。但我们选择只定义 5 种高层类型——Equipment、Material、Abnormal_Condition、Consequence、Mitigation。原因是：

首先，类型越多，LLM 的分类边界就越模糊，越容易出现把一个实体归到两个类型的情况。

其次，我们最核心的查询是因果路径遍历——`MATCH path = (start)-[:leads_to*1..6]->(end)`。这个查询和实体类型无关，只和关系类型有关。所以实体类型的粗粒度不影响核心功能。

最后，5 种类型覆盖了事故因果链的所有关键节点——设备出问题了、物料异常了、状态恶化了、后果发生了、措施在响应。这个粒度已经足够支持问答。」

## 四、Neo4j 存储类（C 重点准备）

### Q8：batch_create_triples() 的作用和实现？

**回答人**：C

「这个方法接收三元组列表，逐条写入 Neo4j——三元组就是形如 (冷却水循环泵, leads_to, 储罐温度持续上升) 的三元。

对每个三元组做三件事。先用 MERGE 创建或匹配起点节点——MERGE 会根据 name 属性检查是否已存在。同样 MERGE 终点节点。最后用 CREATE 创建关系——注意，关系用 CREATE 而不是 MERGE，因为同一对节点之间可能存在多条不同来源的关系。比如"焊接火花 leads_to 爆炸"可能出现在多个不同的事故中，每条关系都有不同的来源报告，不应该被合并。」

## 五、问答匹配类

### Q9：process_question() 的实体匹配逻辑？为什么改了？

**回答人**：C

「这是 app.py 里的核心函数。五步。

第一步——jieba 分词。把用户问题切成词，过滤掉单字。比如"焊接火花有什么危害"变成 ['焊接', '火花', '什么', '危害']。

第二步——打分。遍历图谱所有实体名字，统计有多少分词出现在名字里。比如"焊接火花"这个实体包含"焊接"和"火花"两个词，得 2 分。

第三步——选最佳。这一步我们改过一次。原先直接按分数排序取第一个。但发现一个问题——"焊接火花"和"产生焊接火花"这两个实体都包含"焊接""火花"两个字，同分。按字母序，排在前面的是"产生焊接火花"，但它在 Neo4j 里没有因果路径。用户问问题就匹配到一个死节点。

我们的修复很简单——在同分候选实体中，调用 `neo4j.find_causal_paths()` 检查每个实体有没有出边。有出边的加 3 分 path_bonus。这就保证了匹配到的实体是真正能在图谱里溯源下去的。修复之后，6 个测试问题全部匹配到有路径的实体。

第四步——路径检索。对所有匹配到的实体（最多 8 个），分别用 `retriever.retrieve(entity, max_depth=3)` 搜索因果路径。

第五步——去重和子路径过滤。按路径长度降序排列，如果一个短路径的节点序列完全包含在另一个长路径里，就扔掉短的，只保留长的。这是为了避免重复的碎片路径干扰 LLM 的判断。」

### Q10：_save_to_relational_db() 为什么第一次运行报 column 不存在？

**回答人**：A 或 C

「`AccidentRecord` 的 ORM 模型被更新了，加了 `root_cause`、`consequence`、`related_chemicals`、`related_equipment` 四个新字段。但旧的 SQLite 数据库文件 `chemsafe.db` 是按旧 Schema 建的——表里有 8 个列，没有这 4 个新列。SQLAlchemy 做 query 时生成带新列的 SELECT，SQLite 就报 `no such column`。

修复两步：`del data\processed\chemsafe.db` 然后 `python scripts\init_db.py` 重建。之后流水线就能同时写 TXT 文件、Neo4j 图谱和 SQLite 数据库了。这三个存储是互相独立的，SQLite 出错不影响 Neo4j 写入。」
